Implementation plan · reigner-ui

Reigner UI v1, in five slices

Prompt

Build a clean, minimal but beautiful chat client for Reigner that people can point at their own reigner serve --http server, and that doubles as a reference for anyone building their own Reigner frontend. Users can add several backends, have them persist, switch between them, and see which are unreachable. Build it in working slices rather than a static mockup first, and plan all the slices before writing code.

01

Milestones

Each slice works end to end against dev/indialaw and lands as its own commit or PR. Slices 1–3 use free endpoints only: saved sessions are replayed, never re-run.

Slice 1 · 1–2 days

Event layer, no UI

The part other developers will copy. Plain TypeScript with no React imports.

  • Event types written from reigner/harness/events.py, schema version 2.
  • A ReignerClient for /health, /sessions, /sessions/{id}/events and a streaming run() over fetch.
  • A pure reducer that groups events into rounds: pairs calls and results by call_id, dedupes citations, marks rounds done, asked-to-clarify, failed or interrupted.
  • A port of _tool_summary.py for one-line step summaries.
  • Vitest, with fixtures taken from real dev/indialaw sessions and the captured SSE run.
Done when: npm test passes, and every saved session in dev/indialaw reduces with no unknown-state rounds.
src/reigner/ vitest eventsource-parser
Slice 2 · 1 day

Backends and the app shell

The three-column layout from the mockup, with the backend switcher working for real.

  • Saved backends in localStorage: URL, optional name, last seen.
  • /health polled every 10s per backend, with a 4s timeout. Shows agent name, model, online or unreachable.
  • Add backend dialog: normalizes the URL, probes it, and on failure shows the exact --cors-origin command for this page's origin. "Save anyway" for servers that are down right now.
  • First run with no backends: an empty state that opens the dialog prefilled with http://localhost:8000.
Done when: indialaw on :8000 and indialaw_v1 on :8001 can be added, switched, and one shows unreachable when stopped.

Slice 3 · 2–3 days

Sessions and the read-only conversation

Most of the mockup gets built here, fed by free replays.

  • Routes: /b/:backendId and /b/:backendId/s/:sessionId, so reload and deep links work.
  • Sidebar: sessions sorted by last_updated, grouped Today / Yesterday / Previous 7 days / Older, forks indented under their parent, search over titles.
  • Titles from each session's first question, fetched lazily and cached per backend.
  • Conversation: question, collapsed activity trace, Markdown answer, numbered sources, clarification card, inline errors, "interrupted" marker, token line.
  • Side panel for a source (value, artifact, locator, raw event) or a step (args and result JSON).
Done when: every indialaw session opens from the sidebar and from a pasted URL, and looks like the mockup.

Slice 4 · 2 days

Asking questions live

The composer and streaming. The only slice that needs paid runs, and I'll ask before each one.

  • Send with Enter, new line with Shift+Enter. New sessions read session_id from the first frame and move to its URL.
  • Live trace with a spinner per pending step and an elapsed timer. Stop cancels the request.
  • Runs are tracked per session, so switching sessions mid-run is safe and the composer locks only on the session that's running.
  • Clarification chips send their text as the next question in the same session.
  • HTTP errors before the stream (404, 422, network) as toasts. Error frames during the stream inline in the round.
  • Session list refreshes after each run.
Done when: about 3 paid test runs cover a new session, a follow-up, and a stopped run.

Key code

The three places most likely to go wrong: the round shape, the reducer, and the stream reader.

src/reigner/rounds.ts · the round shape
export type RoundStatus =
  | 'running' | 'answered' | 'clarifying' | 'failed' | 'interrupted'

export interface Round {
  query: string | null          // null when a ?limit= suffix starts mid-round
  steps: Step[]                  // tool_call order; result attached by call_id
  citations: Citation[]          // deduped on source + canonical locator JSON
  notices: Notice[]              // oracle, compaction, steering, status
  answer?: FinalAnswer
  clarification?: Clarification
  error?: { message: string; recoverable: boolean }
  status: RoundStatus
}
src/reigner/rounds.ts · applyEvent
export function applyEvent(t: Thread, e: ReignerEvent): Thread {
  if (e.type === 'user_query') return startRound(closeOpen(t), e.query)
  const r = current(t) ?? orphanRound()   // suffix fetched with ?limit=
  switch (e.type) {
    case 'tool_call':   return put(t, { ...r, steps: [...r.steps, pending(e)] })
    case 'tool_result': // parallel reads finish in any order: match by id
      return put(t, { ...r, steps: r.steps.map(s =>
        s.callId === e.call_id ? complete(s, e) : s) })
    case 'citation':    return put(t, { ...r, citations: addUnique(r.citations, e) })
    case 'final_answer':  return put(t, { ...r, answer: e, status: 'answered' })
    case 'clarification': return put(t, { ...r, clarification: e, status: 'clarifying' })
    case 'error':       return put(t, { ...r, error: toError(e), status: 'failed' })
    case 'oracle': case 'compaction': case 'steering': case 'status':
      return put(t, { ...r, notices: [...r.notices, e] })
    default: return t                        // unknown type: ignore, don't crash
  }
}
// closeOpen(): a round still 'running' when the next user_query arrives,
// or at the end of a replay, becomes 'interrupted'.
src/reigner/client.ts · run()
async function* run(req: RunRequest, signal: AbortSignal) {
  const res = await fetch(`${base}/run`, {
    method: 'POST', signal,                       // abort = Stop; server halts
    headers: { 'content-type': 'application/json' }, // no cookies, no auth
    body: JSON.stringify({ query: req.query, session_id: req.sessionId ?? null,
                          profile: req.profile ?? 'full', state: {} }),
  })
  if (!res.ok) throw await httpError(res)    // 404 unknown session, 422 bad body
  yield* readEvents(res.body!)              // sse.ts: frames → ReignerEvent
}
06

Future scope

Out of v1 on purpose, plus the assumptions this plan makes that you may want to change.

Assumption: which libraries?

eventsource-parser for stream framing, react-markdown + remark-gfm for answers (no raw HTML, so agent output can't inject markup), wouter for routing (tiny, enough for two routes), plain CSS files with the mockup's tokens instead of Tailwind. Per the working rules, slice 1 starts with a short comparison note for the parser, and slice 3 for Markdown and routing; any of these can change then.

Decide with · you · start of slice 1 and slice 3

Assumption: are real sessions OK as committed test fixtures?

The fixtures would contain questions and short quoted passages from the IGNOU and Constitution documents in indialaw. If the repo goes public, you may prefer trimmed or hand-written fixtures instead.

Decide with · you · slice 1

Titles cost one request per session

/sessions has no titles, so the sidebar fetches each session's events to read its first question. Cached forever after (questions don't change), and fetched a few at a time, but the first load of a big backend is slow. A server change that returns the first query in /sessions, or a title endpoint, fixes it properly.

Decide with · Reigner repo · after slice 3

Server features the UI can't offer yet

Delete, rename and fork sessions; open the artifact behind a citation; cost per answer; steering mid-run; auth. Each needs an endpoint in the Reigner repo first. The UI leaves them out instead of faking them.

Decide with · Reigner repo · after v1

No token streaming

Answers arrive whole. The live activity trace is what shows progress, which fits Reigner's "show your sources" story. Streamed text would need a change in Reigner's model adapters.

Cost estimate

Possible by porting reigner/pricing.py and pairing it with the model from /health, but prices drift and a wrong number is worse than none. Token counts only for v1.

Hosting the UI over https

v1 assumes the UI runs locally next to the servers. A hosted https copy calling http://localhost backends runs into browser mixed-content and private-network rules, which vary by browser. Worth a README note once someone tries it.
